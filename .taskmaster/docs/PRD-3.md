# Роли и админ-панель — описание фичи

## О чём фича

После PRD-2 все зарегистрированные пользователи **равны**: каждый видит только
свои транзакции. Для владельца приложения этого недостаточно — нужен
**администратор**, который:

- видит **всех** пользователей, зарегистрировавшихся в приложении;
- может **заблокировать** пользователя (тот не сможет пользоваться приложением);
- может **удалить** пользователя (аккаунт и связанные данные).

Обычные пользователи по-прежнему работают только со своими транзакциями.
Админ получает отдельный раздел `/admin`, недоступный остальным.

## Кто такой администратор

Администратор — **один заранее известный email** (владелец приложения).
Email задаётся в переменной окружения (не в коде и не в UI):

```env
# .env.local (локально) и в Vercel → Environment Variables (прод)
ADMIN_EMAIL=ваш-email@example.com
```

При регистрации или первом входе, если email совпадает с `ADMIN_EMAIL`,
пользователю автоматически выставляется роль `admin`. Все остальные получают
роль `user`.

> **Важно:** замените `ваш-email@example.com` на реальный email владельца
> перед деплоем. Список админов в этой версии **не редактируется** через UI —
> только через env.

## Технический стек (май 2026)

- **Next.js 16** (App Router) + TypeScript — без изменений
- **Supabase Auth** + **`@supabase/ssr`** — сессия и `auth.users`
- **PostgreSQL + RLS** — таблица профилей и политики для админа
- **Service Role Key** (`SUPABASE_SERVICE_ROLE_KEY`) — **только на сервере**
  для операций админа: список всех пользователей, бан, удаление из Auth
- **Server Actions** + **zod** — как в остальном проекте
- **shadcn/ui** — таблица пользователей, кнопки, диалоги подтверждения

## Модель данных

### Таблица `profiles`

Связь 1:1 с `auth.users`. Создаётся при регистрации (триггер или Server Action
после `signUp`).

| Колонка       | Тип        | Описание                                      |
|---------------|------------|-----------------------------------------------|
| `id`          | uuid (PK)  | = `auth.users.id`                             |
| `email`       | text       | email из auth (для списка в админке)          |
| `role`        | text       | `'user'` \| `'admin'`, default `'user'`       |
| `is_blocked`  | boolean    | `false` по умолчанию                          |
| `blocked_at`  | timestamptz| nullable, время блокировки                    |
| `created_at`  | timestamptz| дата регистрации в приложении                 |

Индекс по `email`, `role`, `is_blocked` — по необходимости для админ-списка.

**Назначение роли admin:** при создании/обновлении профиля, если
`lower(email) = lower(ADMIN_EMAIL)` из env (на сервере), выставить
`role = 'admin'`. Иначе `role = 'user'`.

### Связь с транзакциями

Таблица `transactions` уже содержит `user_id` → `auth.users`. При **удалении**
пользователя админом — каскад `on delete cascade` удаляет его транзакции
(как в текущей схеме).

## Главные функции

### 1. Роли: `admin` и `user`

- Роль хранится в `profiles.role`, не в JWT вручную
- Проверка роли **всегда на сервере** (`getUser()` + запрос профиля)
- Обычный пользователь не может вызвать админ-действия, даже подделав запрос
- Админ **не** видит чужие транзакции в этой версии — только список аккаунтов

### 2. Блокировка пользователя

- В админке: переключатель/кнопка «Заблокировать» / «Разблокировать»
- `profiles.is_blocked = true`, `blocked_at = now()`
- Заблокированный пользователь при любом защищённом запросе:
  - middleware или layout проверяет профиль;
  - редирект на `/blocked` с сообщением «Аккаунт заблокирован администратором»
- Заблокированный **не** может создавать/читать транзакции (даже если обойдёт UI)
- RLS: политики `transactions` дополняются условием «профиль не заблокирован»
  (через `exists` по `profiles` для `auth.uid()`)

### 3. Удаление пользователя

- В админке: кнопка «Удалить» + диалог подтверждения (необратимо)
- Server Action с **service role**: `auth.admin.deleteUser(userId)`
- Каскадно удаляются `profiles` и `transactions`
- Админ **не может** удалить сам себя (защита от случайного lockout)
- Админ **не может** удалить другого админа (в этой версии один admin)

### 4. Админ-панель: список пользователей

- Маршрут: `/admin/users` (или `/admin` с редиректом на users)
- Доступ только при `role = 'admin'`; иначе `404` или редирект на `/`
- Таблица колонок:
  - Email
  - Роль (`user` / `admin`)
  - Статус (активен / заблокирован)
  - Дата регистрации (`created_at`)
  - Действия: Заблокировать/Разблокировать, Удалить
- Сортировка по дате регистрации (новые сверху)
- Пагинация — опционально; для MVP достаточно последних 100 записей

### 5. Защита маршрутов

- `/admin/*` — только `admin`, проверка в layout `src/app/admin/layout.tsx`
- Заблокированный пользователь не попадает на `/`, `/dashboard` — только
  `/blocked`, `/login` (signOut), публичные auth-страницы по политике
- Обычный `user` не видит ссылку «Админка» в UI (и не может открыть URL)

### 6. RLS на `profiles`

- **SELECT (свой):** `auth.uid() = id`
- **SELECT (админ):** `exists (select 1 from profiles p where p.id = auth.uid() and p.role = 'admin')`
- **UPDATE (админ):** только поля `is_blocked`, `blocked_at` для чужих профилей;
  пользователь может читать свой профиль, но не менять `role` / `is_blocked`
- **INSERT:** через service role или триггер при signup (не из клиента с подделкой role)

Политики на `transactions` — добавить проверку, что текущий пользователь
не заблокирован (для всех CRUD).

## Этапы разработки (станут задачами Task Master)

1. Миграция: таблица `profiles`, триггер/функция создания профиля при signup,
   backfill для уже существующих пользователей из `auth.users`
2. Логика назначения `admin` по `ADMIN_EMAIL` (серверная, при создании профиля)
3. RLS на `profiles` + обновление RLS на `transactions` (заблокированные)
4. `src/lib/supabase/admin.ts` — service role client; `src/lib/admin.ts` — guards
5. Server Actions: `listUsers`, `setUserBlocked`, `deleteUser` с проверкой admin
6. Страница `/admin/users` + компоненты таблицы и подтверждения удаления
7. Middleware / layout: редирект заблокированных на `/blocked`; защита `/admin`
8. Ссылка «Админка» в шапке только для admin; обновить `AGENTS.md` и `.env.example`
9. Ручная проверка: регистрация второго user, блокировка, вход заблокированного,
   удаление user, вход под ADMIN_EMAIL как admin

## Чего НЕ делаем в этой версии (PRD-3)

- **Несколько админов** с назначением через UI — только один email из env
- **Редактирование ролей** других пользователей вручную (promote to admin)
- **Просмотр транзакций** других пользователей админом
- **Аудит-лог** действий админа (кто кого заблокировал)
- **Приглашения**, организации, команды
- **2FA**, кастомные права (moderator, support)
- **Экспорт пользователей** в CSV
- **Восстановление** удалённого аккаунта

## Дополнительные правила безопасности

- `SUPABASE_SERVICE_ROLE_KEY` и `ADMIN_EMAIL` — **никогда** в клиентском бандле
- Роль и `is_blocked` **никогда** не принимаем из формы/API от клиента
- Удаление и блокировка — только через Server Actions с `requireAdmin()`
- Список всех пользователей — через service role или SECURITY DEFINER view,
  не через ослабление RLS для обычных пользователей
- После block/unblock/delete — `revalidatePath('/admin/users')`
- Сообщения об ошибках для админа — понятные; для атакующего — без утечки
  «существует ли пользователь» (где применимо)

## Критерии приёмки

- [ ] Пользователь с email = `ADMIN_EMAIL` после входа видит раздел «Админка»
- [ ] Обычный user не открывает `/admin/users` (403/404/редирект)
- [ ] В админке отображаются все зарегистрированные пользователи с email и датой
- [ ] Блокировка: user не может пользоваться дашбордом, видит `/blocked`
- [ ] Разблокировка: user снова работает как раньше
- [ ] Удаление: user исчезает из списка, не может войти, его транзакции удалены
- [ ] Админ не может удалить свой аккаунт через UI
- [ ] RLS: обычный user по-прежнему видит только свои транзакции
